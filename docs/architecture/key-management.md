chosen in mission log Q3). Ed25519.

```

RWTEjHpqWTBbbijJKtpGHKoHPXdVAbOkQ+9498maEIr0Cjg5smB6Xd7z
```

- **`key_id`: `6E5B30596A7A8CC4`** — this is the value written into every registry version object
  as `key_id`, and the value ADR-0041 requires for rotation.
- **Verified on receipt, not merely filed:** the public key decodes to exactly 42 bytes
  (2-byte algorithm tag `Ed` + 8-byte key id + 32-byte Ed25519 public key), and the key id
  recovered from the *key material* matches the id in the *comment line*. A mismatch would have
  meant a truncated or hand-edited key file.
- The public key is **meant to be public**: it is embedded in the kernel and launcher later, and
  belongs in documentation and in the site's footer.

### Where the private key lives
- On Ludwig's machine at `~/wom-keys/worldofmodcraft.key`, **unencrypted** (`minisign -G -W`),
  because CI must sign unattended.
- As the GitHub Actions secret **`MINISIGN_SECRET_KEY`** on `worldofmodcraft/registry`, readable
  only by workflows running on that repository's own branches.
- It must never appear in: a repository, a workflow log, an issue or PR, or a chat transcript.
  The two-phase pipeline (mission log Q4) exists precisely so that no fork-triggered workflow can
  reach it.

**Offline backup is Ludwig's responsibility and is not optional.** If the private key is lost,
every future release needs a new key *and* a kernel/launcher update to trust it; existing
signatures remain verifiable, but nothing new can be signed under `6E5B30596A7A8CC4`.

## Rotation procedure (ADR-0041 requires this to be written down)

Rotation does **not** invalidate history: every signature records the `key_id` that made it, and
old artefacts stay verifiable under the old public key. Rotation means "new signatures use a new
key from now on".

1. Generate the new keypair off-CI: `minisign -G -W -p new.pub -s new.key`.
2. Publish the new public key **before** first use: add it to this document and to the site, so
   verifiers can obtain it independently of the artefact they are verifying.
3. Replace the `MINISIGN_SECRET_KEY` Actions secret with the new private key.
4. Leave every historical version object untouched — their `key_id` still names the old key. The
   registry is append-only (ADR-0041); re-signing history would be a rewrite.
5. Kernel and launcher ship a **set** of trusted public keys, not one, so a rotation does not
   strand installed content. Retire an old key only when no supported version references it.
6. Record the rotation here: date, retiring `key_id`, new `key_id`, reason.

## Compromise response
If the private key is believed exposed: rotate immediately (above); publish which `key_id` is
affected and the window; do **not** delete or rewrite existing entries — ADR-0041 forbids it, and
the signatures remain evidence of what was published when. Any artefact signed by the compromised
key after the suspected exposure gets re-examined against its recorded source commit and SHA-256.
